## 1. 结论

两套普通会话路径都有可测试的安全映射方案，但当前源码不能只靠历史中的工具名证明“这是宿主内置工具”。后续接入必须由实际执行注册项产生只含身份的运行时 provenance，并在每次请求中与源记录和最终 wire 结果逐项核对；缺少 provenance 的旧调用、进程重启前调用、来源代际不一致或映射碰撞均跳过。该方案至少支持同一宿主进程中完成的普通 `read`/`grep`/`glob` 调用，不是“所有请求都跳过”。

当前 OpenCode 的 AI SDK 路径还会在共同准备层之后运行 provider 消息变换，其中 Claude/Mistral 会改写调用 ID。共享策略仍在共同准备层生成同一计划，但只有最终 runtime 映射能证明 source/witness、wire 调用 ID 和结果正文一一对应时才能原子应用。OpenAI 等不改写 ID 的 AI SDK 路径以及保持 ID 的 Native 路径可形成正向测试；可能改写或产生碰撞的路径先跳过，不能把原始 ID 写进占位。

S01 没有给不存在的测试环境编造地址。项目的正式测试制品是 `dev` 分支手动 `release-fork.yml` 产生的 prerelease；实现阶段先用绑定 commit 的单平台本地 CLI 做隔离验收，S10 再使用当前 head 的 dev prerelease 安装制品完成交付验收。

## 4. 两套消息体系的字段映射

### 4.1 OpenCode V1 / AI SDK 形状

| 语义 | 原记录 | wire 位置 | 资格 / 跳过规则 |
| --- | --- | --- | --- |
| message 身份 | `WithParts.info.id` | 转换后的 assistant message `id` | 必须唯一且映射到同一消息 |
| part 身份 | `ToolPart.id` | 适配器侧映射键，不一定直接出现在 provider payload | 缺失、一对多不明或重复则该项跳过 |
| 调用身份 | `ToolPart.callID` | `toolCallId`；见 `message-v2.ts:317-325` | 最终 wire 中 call/result 必须各唯一且成对 |
| 工具名 | `ToolPart.tool` | `tool-<name>` / tool-call name | 名称不能证明来源；只允许 provenance 确认的内置 `read|grep|glob` |
| 成功状态 | `state.status === "completed"` | `output-available` / tool-result | pending/running/error/interrupted 全部跳过 |
| 完整输入 | `state.input` | tool-call input | 规范化失败、缺字段语义不明或 provider 改写则跳过 |
| 正文 | `state.output` | string 时 `ToolResultValue.text` | 必须为未截断、未 compact 的完整纯文本；逐字相等 |
| 附件 | `state.attachments` | 可能抽成 synthetic user media | 任一附件/媒体均跳过 source 与 witness |
| 指令来源 | `read` 的 `state.metadata.loaded`；输入 `filePath` basename | 不单独出现在 wire | `loaded` 非空，或目标 basename 为受保护指令文件，均跳过 |
| provider 执行 | `part.metadata.providerExecuted` | `providerExecuted` | true 或未知 provider 语义均跳过 |
| 步骤边界 | assistant parts 中 `step-start` / `step-finish`；schema 见 `session-v1.ts:233-257` | `step-start` 转换时只作结构边界 | 从原记录分步；边界不闭合则扩大到整条 assistant message 保护 |
| 旧 prune | `state.time.compacted` | 固定旧清理文本 | 不能作为 source 或 witness，不写回该字段 |

V1 schema 的成功状态、正文、附件、callID 和工具名见 `packages/schema/src/session-v1.ts:277-325`；实际转换见 `packages/opencode/src/session/message-v2.ts:292-325`。`read` 会把动态加载的 instruction 路径记录在返回 metadata 中（`packages/opencode/src/tool/read.ts:300-315`），因此该字段必须在候选提取阶段参与保护。

### 4.2 Core SessionMessage / canonical LLM 形状

| 语义 | 原记录 | wire 位置 | 资格 / 跳过规则 |
| --- | --- | --- | --- |
| message 身份 | `Assistant.id` | canonical assistant message `id` | 必须唯一 |
| part 定位 | `Assistant.content[index]` | 同一 assistant content / 后续 tool message | 使用 `{messageID, contentIndex, callID}`；不能只靠数组位置 |
| 调用身份 | `AssistantTool.id` | `ToolCallPart.id` 与 `ToolResultPart.id` | 必须一一对应，见 `to-llm-message.ts:30-67` |

| 成功状态 | `state.status === "completed"` | `ToolOutput.toResultValue` | error/pending/running/provider-executed 跳过 |

### 4.3 内置来源的可测试方案

当前 V1 `ToolPart` 和 Core `AssistantTool` 都只持久化 name/callID，没有宿主内置、custom、MCP 或 provider 的不可伪造来源。OpenCode registry 先返回 builtin 再返回 custom（`tool/registry.ts:241-274`），随后 `SessionTools.resolve` 还会按相同 key 写入 MCP 工具（`session/tools.ts:552-559`）；Core local registration 也会覆盖 application registration（`core/src/tool/registry.ts:105-119`）。所以历史中的 `tool === "read"` 不足以放行。

S05/S06 必须实现以下运行时 provenance 契约：

1. 工具 materialization 产生不可由插件输入伪造的内部 source descriptor：`host-builtin`、`custom`、`mcp`、`provider`，并包含当前 registration identity/generation。
2. 实际结算成功时，将 `{sessionID, assistantMessageID, callID, toolName, sourceKind, generation}` 写入 location/session 生命周期内的有界 provenance ledger；不得保存输入、输出、路径或指纹，不得跨 session 查询，不持久化。
3. 规划时 source 与 witness 均必须命中同一 ledger、同一 host-builtin registration generation，并与当前消息的 messageID/callID/name 对齐。
4. session 删除、instance 关闭或 registration generation 变化时清除；进程重启前的旧调用没有记录，因此跳过。这是执行来源能力，不是重复内容缓存。
5. 正向集成测试在同一运行时完成两个合格内置调用并证明可折叠；重启、custom 同名、MCP 同名和 local override 测试证明跳过。

若实现评审认为任何跨请求内存身份记录也违反“每次请求独立计算”，必须先修订规格并选择持久化、host-signed provenance 或更严格功能收缩；不得退回按名字猜测。动态比较、分组、正文和折叠计划本身仍必须每次请求独立计算。

## 5. 最终 wire 映射与预算

### 5.1 OpenCode

`LLMRequestPrep.prepare` 在 `packages/opencode/src/session/llm/request.ts:56-205` 完成 system transform、provider options、`chat.params`、工具过滤/strict 处理和排序。计量输入必须来自该准备结果：

- `prepared.messages`；其中非 OAuth system 已作为 system message 插入。
- OAuth 的 `prepared.params.options.instructions`；与 `prepared.system` 只计一次。
- `prepared.tools` 的名称、描述和 JSON schema；不得序列化 execute closure。
- `prepared.params.maxOutputTokens`，配合 `model.limit.input/context`。
- 必要协议开销；媒体或无法估算内容使整次请求跳过。

Native adapter 在 `native-request.ts:181-193` 形成 canonical `system/messages/tools/generation`。AI SDK 在 `llm.ts:324-339` 之后仍执行 `ProviderTransform.message`；Claude 与 Mistral 的调用 ID 改写见 `provider/transform.ts:210-266`。因此计划必须携带 prepared generation/model/tool fingerprint，发送前校验；实际 runtime 可能改写调用 ID、改变 message 顺序/内容或产生 ID 碰撞时，以 `mapping-mismatch` 返回未投影的原请求。已知不改写 ID 的 provider/runtime 才能成为首批正向矩阵。

### 5.2 Core

Core 在 `runner/llm.ts:336-346` 得到完整 `LLM.Request`，现有 compaction 已按 `system/messages/tools` 做一次 `Token.estimate(JSON.stringify(...))`（`session/compaction.ts:79`、`:230-240`）。动态折叠应复用同一个共享估算器和该完整请求，输出预留取 `request.generation.maxTokens`，否则取 route output limit；上下文来自 route limits。先生成独立投影给本次发送/预算判断，摘要仍读原始 `entries`。

### 5.3 软预算与失效条件

使用规格中的 `U = min(inputLimit ?? context, context - outputReserve)`、`T = floor(U * 0.7)`。必要值无效、output reserve 未知、system 重复计量无法排除、工具 schema 无法序列化或存在未知媒体时整次跳过，不把 unknown 当 0。

以下任一变化使旧计划失效并返回原请求：purpose、model/route/runtime、最终 max output、system/instructions、工具集合或 schema、消息数量/顺序、source/witness 身份、provider call-ID 变换、wire 文本位置、provenance generation。网络重试复用同一已验证请求快照；真正的新 provider turn 重新规划。

当前共享估算器仅为 `round(chars / 4)`（`packages/core/src/util/token.ts:3-5`）。它是保守触发估算，不是 tokenizer 或硬窗口证明。规划器尚不存在，因此 S01 不能伪造比较工作量基准或固定数字；S03 必须以总 UTF-8 输入字节、候选数和碰撞桶为轴建立基准并固定上限。在该上限落地和通过退化输入测试之前不得把默认开启能力接入产品；一旦计数超限，固定跳过原因 `work-limit`，不得降级为近似比较。

schema 中 `dynamic` 和 legacy `prune` 都必须保持 optional，不能写 schema 默认值破坏“显式/未设置”区分。先完成分层合并，再解析一次有效开关。
