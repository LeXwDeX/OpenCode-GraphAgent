### Core manual-compaction public API limitation (source-verified)

`packages/core/src/session/compaction.ts` exposes exactly `compactIfNeeded` (automatic threshold; gated on `config.auto` and the model context limit) and `compactAfterOverflow` (overflow recovery). Both are invoked only by `packages/core/src/session/runner/llm.ts` (pre-turn threshold check and the overflow retry path), and both publish `Compaction.Started`/`Ended` with the hardcoded `reason: "auto"`. Core has **no public manual-compaction entry point**, so no Core manual path is claimed or simulated here; manual full compaction (`reason: "manual"`, `auto: false`) is covered only at the OpenCode layer, where `packages/opencode/src/session/compaction.ts` implements it. Existing projector-level tests that publish compaction events directly (for example `session-runner-hotpath.test.ts` "resets the history cursor after compaction" and the `session-runner.test.ts` compaction suite) are retained from the approved base as projection/lifecycle coverage, labelled as such, and are no longer presented as end-to-end compaction evidence.

## Completed-tool-state structured fallback

- Change: `serializeCompletedToolState` (new, `compaction.ts:91-95`) prefers `serializeToolContent(state.content)`; when that is empty and `state.structured` is non-empty it returns `JSON.stringify(state.structured)`; both empty returns `""` (previous behavior). `serialize` (`compaction.ts:111`) now calls it for completed tool parts.
- Why: a completed tool with structured-only output previously serialized to an empty string, silently dropping the tool result from summary inputs.
- Truncation behavior is unchanged: the fallback string passes through the same `truncate` bound (`TOOL_OUTPUT_MAX_CHARS = 2_000` chars, then `[truncated]`) that text content always used; both new summary-input assertions require ≥4 `[truncated]`/truncation markers.
- Unwanted-data exposure evaluated against the actual producer and to-LLM contracts, not a generic schema argument:
  - Producer: `state.structured` is `Record<string, Any>` (`packages/schema/src/session-message.ts:98`), written only from real tool settlement events (`packages/core/src/session/message-updater.ts`, `session.next.tool.success/progress`); it is the tool's own durable structured output, not an internal object graph.
  - To-LLM conversion: in ordinary conversation the Core runner already lowers a completed tool to `ToolOutput.toResultValue({ structured, content })`, and `packages/llm/src/schema/messages.ts:104-109` returns `{ type: "json", value: output.structured }` whenever `content` is empty — i.e. the provider already receives this exact record verbatim in normal turns; error results also embed `structured` (`to-llm-message.ts:71`).
  - Therefore the fallback exposes no data the provider has not already seen in the normal path; its only consumers are summary prompt inputs (`buildPrompt` → `Message.user(summaryPrompt)`), which already contain the serialized conversation, under the same 2,000-char bound. Content precedence is preserved (non-empty content wins), and a regression asserts a base64-style `structured.content` payload is **not** emitted when bounded text content exists.
- Regressions added only for the demonstrated gap: `packages/core/test/session-compaction.test.ts` gained two focused cases (fallback used when content empty; content preferred over structured). No further regression was added because no to-LLM contract gap was demonstrated.
